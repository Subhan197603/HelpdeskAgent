# 1. Human Approval Protocol

## 1.1 Mandatory Pause

Before implementation, Codex must present a bounded plan and stop for the exact
plan-approval phrase defined for the task. Plan approval authorizes only the
planned implementation; it does not authorize a commit, tag, push, deployment,
or another task.

After implementation and full validation, Codex must stop and display:

```text
TASK REVIEW READY

Completed task: Milestone X, Task X.Y — <name>
Validation result: PASS | FAIL
Commit status: uncommitted
Recommended next task: Milestone A, Task A.B — <name>

To approve the commit, tag, verification, and push, reply exactly:
APPROVE MILESTONE X TASK X.Y COMMIT

To reject or request changes, describe the required corrections.
```

Codex must not commit, tag, push, or begin another task until the exact current
approval is received.

## 1.2 Approval Meaning

When the owner gives the exact plan-approval phrase, Codex may implement only
the approved plan, validate it fully, and stop for commit approval.

When the owner then replies:

```text
APPROVE MILESTONE X TASK X.Y COMMIT
```

Codex must:

1. Reconfirm the working tree contains only that task's changes.
2. Run `git diff --check`.
3. Run the task's fast pre-commit checks.
4. Stage only relevant files.
5. Review the staged diff.
6. Commit using the task registry's commit message.
7. Create the task registry's annotated or lightweight tag according to the
   repository's existing convention.
8. Verify the commit and tag.
9. Push the verified commit and tag when push is in scope.
10. Stop and await a separately planned and approved next task.

Neither approval authorizes Codex to begin a future task automatically.

Single approval phrases retained in completed historical task gates record the
workflow used at the time. They are not active authorization and must not be
reused to bypass the current plan and commit approval gates.

## 1.3 Rejection or Correction

When the owner requests changes:

- Make only the requested or necessary in-scope corrections.
- Rerun affected checks.
- Rerun the full gate when the correction can affect security, migrations,
  database behavior, authorization, public APIs, or generated contracts.
- Present the review-ready report again.
- Do not commit without a new approval.

## 1.4 Prohibited Assumptions

Codex must not interpret any of the following as approval:

- "Looks good"
- "Continue"
- "Next"
- "Proceed"
- Silence
- A previous approval for another task
- A completion report generated by Codex itself

Only the exact current-task approval phrase is sufficient.

## 2.1 Status Rules

### COMPLETED

A task is completed only when:

- Its implementation exists.
- Its required tests exist.
- Its required documentation exists.
- All required checks pass.
- Its commit exists.
- Its expected tag exists.
- No uncommitted files belonging to the task remain.

### IMPLEMENTED_VALIDATED_UNCOMMITTED

Use this status only when:

- Implementation is present.
- Full required checks pass in the current working tree.
- The task has not been committed.
- No unrelated changes exist.

### BLOCKED

Use this when:

- A specification conflict exists.
- A secret or credential is detected.
- Alembic history is conflicting.
- A destructive migration requires unapproved data loss.
- Tenant isolation cannot be proven.
- Required infrastructure is unavailable and cannot be safely replaced.
- The working tree contains unrelated changes that cannot be separated.
- A task requires a deferred feature not authorized by the roadmap.

# 3. Global Definition of Done

Every task must satisfy all applicable items.

## 3.1 Architecture

- Preserve modular-monolith boundaries.
- Keep routers/controllers thin.
- Put use-case coordination in application services.
- Put business invariants in domain services or aggregates.
- Put SQL in repositories or database adapters.
- Avoid generic arbitrary-table repositories.
- Do not expose ORM entities directly through APIs.
- Preserve PostgreSQL as the system of record.
- Preserve object storage for file bodies and raw MIME payloads.
- Preserve Redis as non-authoritative infrastructure.
- Preserve exact configuration-version references at runtime.

## 3.2 Database

- Do not modify the physical baseline after adoption.
- Use Alembic for every post-baseline schema change.
- Keep migration history linear unless an approved branch/merge is documented.
- Use explicit schemas, constraints, and index names.
- Include downgrade logic unless explicitly impossible and approved.
- Run destructive-migration checks.
- Test upgrade, downgrade, and re-upgrade.
- Use UTC `timestamptz`.
- Preserve append-only event, audit, evidence, decision, and tool-call history.
- Do not store secrets, raw attachment bytes, or raw email MIME bodies in
  PostgreSQL.

## 3.3 Security

- Enforce authentication and centralized authorization.
- Enforce tenant isolation.
- Use non-owner runtime roles.
- Preserve transaction-local tenant and user context.
- Prevent pooled-connection context leakage.
- Treat RLS as defense in depth, not a substitute for service authorization.
- Validate all client-controlled identifiers server-side.
- Never trust client-provided roles, tenant IDs, permissions, status IDs,
  workflow versions, routing versions, priority, or AI tool permissions.
- Do not log tokens, credentials, raw prompts, document bodies, email bodies,
  attachments, or sensitive personal information.
- Use RFC 7807 error responses with correlation IDs.
- Preserve production safety checks for developer identity and diagnostics.

## 3.4 Quality

Run all applicable configured checks:

- Ruff format
- Ruff lint
- mypy strict
- Python unit tests
- PostgreSQL integration tests
- Identity, OIDC, authorization, and RLS regression tests
- Alembic upgrade/downgrade/history/policy checks
- OpenAPI validation
- Prettier
- ESLint
- TypeScript strict checking
- Vitest
- Playwright when frontend behavior exists
- Docker Compose validation
- API and worker image builds
- Container health/readiness checks
- Gitleaks
- pip-audit
- pnpm audit
- Trivy filesystem and image scans
- `git diff --check`

GNU Make is unavailable on the Windows host. Run the underlying commands
directly and validate Makefile targets through the established container-based
method.

## 3.5 Documentation

Update as applicable:

- API documentation
- OpenAPI contract
- developer guide
- operations guide
- security guide
- migration guide
- module design
- test commands
- configuration reference
- known limitations
- deferred scope
